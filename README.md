# Multicluster-Runtime Provider

This repo contains an implementation of [multicluster-runtime](https://github.com/kubernetes-sigs/multicluster-runtime)'s `Provider` interface which is compatible with the [open-control-plane cluster API](https://github.com/openmcp-project/openmcp-operator/blob/main/api/clusters/v1alpha1/cluster_types.go).

## Usage

### How it works

The provider is basically a small controller that watches `AccessRequest` resources on the platform cluster, fetches their kubeconfig secrets, and caches the clients built from them, which can then be retrieved via its `Get` method.

The provider works on existing `AccessRequest` resources, instead of watching `Cluster` resources and managing `AccessRequest`s itself. These are the reasons for this decision:
- Managing cluster access is out of scope for a multicluster-runtime `Provider` implementation.
- The creator of `AccessRequest` resources needs to delete them too, and the provider cannot do this, as it would need to be notified when the operator it is used by has finished cleaning up resources on the cluster. Deleting the `AccessRequest` before this point would prevent proper cleanup, not deleting the `AccessRequest` can block `Cluster` deletion due to finalizers.
- The operator using this provider needs an extra controller watching `Cluster` resources anyway, because it cannot retrieve cluster lifecycle information (e.g. when a `Cluster` gets a deletion timestamp) from the provider. Having this controller manage cluster access is therefore no big overhead.

#### Caveat: Cluster-AccessRequest Relationship

Watching `AccessRequest` resources instead of `Cluster` ones comes with an issue, though: There can be more than one `AccessRequest` per `Cluster`, but the `Provider` interface requires a 1:1 relation between cluster identities and clients. As kubeconfigs generated by `AccessRequest`s can have different permissions, it is important which one is used and the provider has no means to decide for one, if it gets multiple `AccessRequest`s for the same `Cluster`.

This is solved via the list of label selectors, which can be passed into the provider via the options of its `New(...)` constructor. Only `AccessRequest`s which match at least one of the provided label selectors will be fetched by the provider. **The controlling operator needs to pass in a set of label selectors which never match more than one `AccessRequest`s for the same `Cluster`.**

> [!NOTE]
> If the provider fetches an `AccessRequest` for a `Cluster` for which the provider already has registered a different `AccessRequest`, it will log an error and ignore the second `AccessRequest`. This means that the used kubeconfig in this situation depends on the order in which the conflicting `AccessRequest`s are read, rendering the provider's behavior potentially unstable.

> [!WARNING]
> Opposed to most other controllers working with label selectors, not specifying any label selector causes the provider to ignore _all_ `AccessRequest`s.

### Recommended Setup

The easiest way to consume the provider is to initialize it in combination with a cluster controller:
```go
  import (
    "github.com/openmcp-project/multicluster-provider/pkg/provider"
    clusterhandler "github.com/openmcp-project/multicluster-provider/pkg/cluster"
  )

  ...

  prov, cctrl := provider.NewWithClusterController(
    platformCluster,
    providerName,
    scheme,
    &clustersv1alpha1.TokenConfig{ // adapt to required permissions
      Permissions: []clustersv1alpha1.PermissionsRequest{
        {
          Rules: []rbacv1.PolicyRule{
            {
              APIGroups: []string{"*"},
              Resources: []string{"*"},
              Verbs:     []string{"*"},
            },
          },
        },
      },
    },
    clusterhandler.Funcs{
      IsResponsibleForFunc: ..., // cluster selector
      HandleCreateOrUpdateFunc: ..., // what to do on create/update
      HandleDeleteFunc: ..., // what to do on delete
      AfterDeletionFunc: ..., // what to do after the cluster is gone
    },
  )

  mgr, err := mcmanager.New(platformCluster.RESTConfig(), prov, ...)
  if err != nil {
    return fmt.Errorf("unable to create manager: %w", err)
  }
  if err := cctrl.SetupWithMulticlusterManager(mgr); err != nil {
    return fmt.Errorf("unable to setup multicluster Cluster controller with manager: %w", err)
  }
	if err := prov.SetupWithManager(mgr.GetLocalManager()); err != nil {
		return fmt.Errorf("unable to setup multicluster provider with manager: %w", err)
	}
```

This approach not only creates a controller that watches `Cluster` resources and creates `AccessRequests` for it and wires it to the provider, but it also allows to inject own logic into the cluster controller via the given cluster handler (last argument of the constructor). If no custom logic is required in the cluster controller, simply use an empty `clusterhandler.Funcs` object.
